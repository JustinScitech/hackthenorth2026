# Underwriting evaluation corpus

The project has two distinct evaluation surfaces:

1. `npm run eval:underwriting` evaluates the Federato 2025 sample commercial property appetite scorer offline. The versioned cases in `evals/underwriting-appetite.json` assert the final recommendation, score, and all eight factor statuses. The command exits nonzero on a mismatch and writes a detailed, ignored report to `data/underwriting-eval-report.json`. `npm test` runs the same corpus.
2. `npm run eval:agent` evaluates Gemini extraction of original building year and three-year **claim count** from broker text, then checks the shared carrier appetite rules. It includes four built-in synthetic cases and every JSON file in `evals/agent-notes/`. The live run requires `GEMINI_API_KEY`; it fails if the model is unavailable or if the selected result falls back to the parser. `npm test` validates the versioned note samples against the parser and deterministic review rules without a model key.

Cases and Federato triage share one appetite scorer. A five-year **dollar loss value** from Federato guidance must never be treated as a three-year claim count in the case-review agent. The current application accepts text notes, not PDF uploads; a PDF excerpt added to a text fixture tests extraction from that excerpt, not PDF ingestion, OCR, or layout understanding.

## Adding the underwriting PDFs

For each supplied PDF, record its title, date or version, and page number before creating expectations. Extract text and inspect tables visually so columns, footnotes, and threshold symbols are preserved. Use a human-reviewed rule as the expected answer; do not generate the expected result by running the scorer being evaluated. Mark missing, conflicting, or unspecified facts as unknown and preserve the underwriter review step.

- For appetite rules and sample policy data, add a case to `evals/underwriting-appetite.json`. Set `rule`, a fictional `patch` over the base policy, `expected.recommendation`, `expected.score`, changed factor statuses, and a case `source` with the PDF title and page. The base statuses supply expectations for unchanged factors. If a new document changes the guideline version, first update the scorer and the corpus version together; do not quietly mix incompatible versions.
- For narrative submissions or loss runs, add a JSON array to `evals/agent-notes/`. Each item needs a unique `id`, a `source` with PDF title and page, a short anonymized `notes` excerpt, `expected` construction year and three-year claim count, intake fields, all eight `expectedFindings`, and `needsBroker`. `expected` may also carry any carrier appetite field the note states in prose (`premium`, `lossValue`, `lossHistoryComplete`, `business`, `line`, `constructionPercent`, `effective`, `expiration`); the offline extraction eval scores those against the parser floor and records prose-only ones as known failures until a model run reads them. The loader validates these fields and rejects duplicate IDs.
- For the Federato query documentation, `src/federato/triage.test.ts` checks the Auth0 domain, schema action, query envelope, pagination, and pass-through of `where → expand → unwind → filter → over → select → sort → pagination`, including `$elemMatch` for arrays. These tests use a fake HTTP handler and no credentials. The app's triage planner currently uses only the pipeline stages needed for its ranking; the client accepts the full documented request shape.

Run `npm run typecheck`, `npm test`, and `npm run eval:underwriting` after each document batch. Run `npm run eval:agent` with a model key when checking model extraction. Keep source PDFs and real submission data out of Git unless sharing is authorized; fixtures here use fictional examples and short excerpts. The supplied Appetite Guidelines page 2 was visually reviewed to verify table-column placement, including renewal business under Not Acceptable.
